AI-Augmented Kubernetes Operations

Repetitive cluster work specified as PRDs and encoded as reusable AI skills, so operational knowledge lives in version control instead of in whoever did it last.

  • 20+operations encoded as AI skills
  • 40%+operational toil eliminated
  • 30+EKS clusters operated this way

Problem

Running 30+ EKS clusters for 100+ engineering teams means doing the same work over and over: validate an add-on upgrade, roll a Kubernetes version through the fleet, stand up a cluster, tear one down, work out why a node pool is misbehaving. Each of those is well understood by whoever performed it last and largely opaque to everyone else. The knowledge lived in people's heads and in runbooks that went stale between uses, which made experienced engineers a bottleneck for routine work — and made routine work risky whenever they were unavailable.

Approach: the PRD comes first

I treated each recurring operation as a product rather than a script. Every one begins as a PRD — what the operation must do, what it must never do, what "done" looks like, which failure modes it has to detect and how it should behave when it hits one — and only then becomes an AI skill that implements it. Writing the requirement down first is what makes the automation reviewable. The spec is the artifact the team argues about and signs off on; the skill is just the implementation of an agreement that already exists.

Approach: what the skills cover

The skills target the operations that repeat most. Rollout and upgrade testing validates a version bump against a canary cluster and verifies its health before it advances to the next wave. Cluster lifecycle skills handle provisioning through decommissioning. Incident skills do first-pass investigation, gathering Datadog and kubectl context before a human joins the call. Capacity and cost skills surface right-sizing candidates and idle resources — the analysis layer underneath the cost work. All of them chain tools already in the stack, in Python and Bash, so nothing new had to be adopted for any of it to work.

Impact

20+ encoded workflows and a 40%+ reduction in operational toil. Upgrade work changed shape most visibly: validating a version bump went from half a day of manual checking to a repeatable, reviewable procedure that produces the same evidence every time. The more durable outcome is that because every skill has a PRD behind it, the fleet's operational knowledge now sits in version control where it can be reviewed, corrected, and improved — rather than in the memory of whoever happened to run it last.
