  1. 01

    AI-Augmented Incident Operations

    Institutional knowledge, encoded as executable workflows instead of documentation nobody reads at 3am.

    Problem

    Across 30+ EKS clusters serving 100+ engineering teams, incident response depended on knowledge that lived in individual engineers' heads. Every investigation started from zero — the same Datadog queries, the same kubectl checks, the same scramble for context. The engineers who knew where to look became bottlenecks during exactly the moments when speed mattered most.

    Approach

    Rather than writing more runbooks that go unread under pressure, I made the knowledge executable. Built 20+ AI-assisted workflows in Python and Bash chaining Datadog, kubectl, and Terraform — incident response playbooks that gather context before a human joins the call, cluster decommission runbooks, security triage protocols. Generative AI applied precisely where judgment is expensive and pattern-matching is cheap: first-pass incident investigation, postmortem drafting from timeline data, and runbook authoring from real remediation steps.

    Impact

    Operational toil down 40%+, with context-switching during incidents dropping sharply because the first ten minutes of investigation now happen before anyone reads a page. The more durable outcome is that the knowledge stopped being tribal — an engineer in their first on-call rotation starts an investigation from the same place a tenured one does.

  2. 02

    Multi-Region EKS Platform at Scale

    Full lifecycle ownership of 30+ production clusters, changed without downtime.

    Problem

    Thirty-plus production Kubernetes clusters across multiple AWS regions, serving 100+ engineering teams who ship continuously. Any platform change — a Kubernetes version bump, a CNI upgrade, an add-on rollout — is simultaneously a change to every team's production environment. A bad rollout doesn't break one service; it breaks the company.

    Approach

    A wave-based rollout strategy: changes propagate through defined cluster tiers with bake time and health verification between waves, so a regression surfaces in a low-stakes wave long before it reaches revenue-critical clusters. Terraform as the single source of truth across the fleet, enforcing cloud security standards and SOX-compliant governance uniformly rather than cluster by cluster. Core platform stack of Cilium for networking, Istio for service mesh, and ArgoCD for GitOps-driven delivery. Karpenter for node provisioning, including GPU-aware node pools that match compute allocation to the actual shape of the workload instead of a static guess.

    Impact

    Zero-downtime infrastructure changes across the production fleet, and 100+ teams shipping without thinking about the platform beneath them — which is the entire point of the job.

    • Istio

  3. 03

    Reliability as a Measurable Practice

    Turning "we should be more reliable" into a budget teams can actually plan against.

    Problem

    Reliability without numbers is an opinion, and opinions lose to feature deadlines. Teams knew incidents were bad but had no shared, quantitative basis for deciding when stability should outrank velocity — so the decision defaulted to velocity every time, until something broke badly enough to reset the argument.

    Approach

    Defined SLIs, SLOs, and error budgets grounded in EKS cluster health metrics and add-on component monitors across the fleet, then tied error budget consumption directly to feature prioritization — when the budget is spent, reliability work takes the slot, and that is a rule rather than a negotiation. Owned the incident lifecycle end to end: detection, response, communication, postmortem quality, and follow-up completion for high-severity customer-facing incidents. Ran reliability reviews for high-risk changes and new services covering production readiness, capacity, failure modes, and rollback — framed as teaching rather than gatekeeping, because a review that only blocks does not scale to 100+ teams. Mentored 3+ SREs and codified production readiness checklists and on-call standards built to outlive my involvement.

    Impact

    Repeat incidents declined through blameless postmortems that produced genuine follow-through rather than tickets nobody closes. Reliability became something teams could plan against instead of a value they were told to hold. The checklists and on-call standards persisted after I stepped back — the only real test of whether a practice took.

    • SLIs & SLOs
    • Error budgets
    • Incident command
    • Blameless postmortems
    • Production readiness reviews
    • Datadog
  4. 04

    SOX-Compliant Cluster Decommissioning

    A reusable teardown framework where the audit trail is a byproduct of execution, not archaeology.

    Problem

    Decommissioning production infrastructure in a SOX-regulated environment is mostly not a technical problem. The teardown itself is straightforward. Proving to auditors that the right approvals happened, the right stakeholders were notified, and nothing was destroyed that shouldn't have been is where these projects stall for months — which is why dead clusters keep running and keep costing money.

    Approach

    Designed an end-to-end process covering governance, documentation, stakeholder coordination, and technical teardown, structured so the audit evidence is produced as the work happens rather than reconstructed afterward. Then generalized it into reusable frameworks for both EKS clusters and standalone cloud assets — EC2, RDS, EBS — so the next decommission is a checklist execution rather than a project with a kickoff meeting.

    Impact

    Repeatable, audit-ready decommissioning. Spend recovered from retired infrastructure without the compliance exposure that normally keeps unused clusters alive indefinitely.

    • Terraform
    • AWS
    • SOX governance
    • EC2 · RDS · EBS
    • Stakeholder coordination
  5. 05

    Zero-Downtime Platform Migration at Intuit

    Moving live contact-center voice, video, and chat to AWS in 60 days without dropping a call.

    Problem

    Intuit's Virtual Expert Platform — the voice, video, and chat contact-center services behind every Intuit product — ran on a self-hosted platform that had to move to AWS on a fixed timeline. Contact center traffic cannot be paused for a maintenance window. A customer mid-call with a tax expert is not a connection you are allowed to drop.

    Approach

    Architected a multi-region AWS target with failure isolation, so a regional failure degrades the service rather than ending it. Built the observability layer first — Datadog, Prometheus, and Grafana across 1,000+ nodes — because you cannot safely migrate what you cannot see, and a migration without baselines is a guess. CI/CD through Spinnaker, ArgoCD, Docker, and Kubernetes automating commit to production. Kubernetes adoption included OPA policy enforcement, federated deployments, and custom resource definitions for the platform's distributed components.

    Impact

    Migration completed in 60 days with zero downtime, and the self-hosted platform decommissioned on schedule rather than lingering as a parallel system. Mean time to detect incidents down 30%. Structured root-cause analysis and blameless postmortem practice established across voice, video, and chat — materially changing how the organization learned from failure.

    • AWS
    • Kubernetes
    • Spinnaker
    • ArgoCD
    • Datadog
    • Prometheus
    • Grafana
    • OPA
  6. 06

    Fraud-Detection Infrastructure at USAA

    Cutting a three-week deployment cycle to one day in an adversarial, real-time domain.

    Problem

    Real-time fraud detection is adversarial — attack patterns shift faster than release cycles, so the speed of your deployment pipeline sets a hard ceiling on how quickly detection logic can adapt. Infrastructure changes took three weeks to reach production. Improvements sat in a queue while fraud moved.

    Approach

    Automated the infrastructure services with Chef, Ansible, Python, and Bash, and designed custom core services to replace the fragile hand-configured ones. Led adoption of blue/green deployments paired with production readiness reviews, so shipping faster did not mean shipping less carefully. Automated the fraud-detection batch pipelines themselves in Java and Python across 15+ monthly jobs, and administered identity governance — RBAC, SSO via OKTA, SAML, OAuth — across the Linux estate.

    Impact

    Deployment time down 15x, from three weeks to a single day. Infrastructure stability and reliability improved 35–70% depending on account and workload. False positives in the batch fraud pipelines reduced 30% — which in fraud detection means fewer legitimate customers wrongly blocked.

    • Chef
    • Ansible
    • Python
    • Java
    • Blue/green deploys
    • RHEL
    • OKTA · SAML · OAuth
